## 启动流程（Boot Sequence）

从上电到你能和机器人对话，中间大概经历这些步骤：

```
1. main()                                     — FreeRTOS 调度器启动
2. Application::Initialize()                  — 初始化协议对象
3. Board::Initialize() (各板型构造函数)       — 初始化 SPI / I2S / UART / 舵机 / IMU / 显示屏 / 摄像头
4. Board::InitializeTools()                   — ★ 各板型在这里注册 MCP 工具
5. McpServer::AddCommonTools()                — 添加通用工具（音量、亮度、电源、摄像头等）
6. McpServer::AddUserOnlyTools()              — 添加仅给用户看的工具（重启、AEC 配置等）
7. AudioService 启动唤醒词检测循环            — 本地离线跑 AFE wake word
8. WiFiManager 连接 WiFi                      — 或进入 BluFi 配网模式
9. OTA 检查新版本                              — 同时获取 MQTT/WebSocket 地址
10. Protocol.Start()                          — 连接云端 WebSocket/MQTT
11. Board::OnStartup()                        — 播放开机音效 + 表情动画
12. Application::Run()                        — ★ 进入主事件循环，永远不返回
```

### 第 4 步的关键细节

每个 Board 类都有一个 `InitializeTools()` 方法，在这里把自己形态专属的运动能力注册成 MCP 工具。

PuppyBoard 注册了 20+ 个工具：
- `self.dog.move`（前后/转向）
- `self.dog.set_motor_angle`（即兴设定每个舵机角度）
- `self.dog.Wave`、`self.dog.Naughty`、`self.dog.Swing`、`self.dog.Sit`……（预设动作）
- `self.dog.calibrate`（标定舵机零点）
- `self.laser.control`（激光剑开关）
- `self.ble.remote_control`（开启/关闭蓝牙遥控）

HoverBoard 注册的工具：
- `self.robot.move`（前进后退）
- `self.robot.rotate`（原地旋转）
- `self.robot.head_angle`（抬头/低头）
- `self.robot.set_mode`（平衡小车 ↔ 云台模式）
- `self.robot.pitch`（云台俯仰）
- `self.status.battery`（查电量）

## 主事件循环（Application::Run）

这是整个固件的"心脏"。它跑在 FreeRTOS 主任务里，用 `EventGroup` 等事件，然后 dispatch 到对应的 Handler：

```cpp
// 伪代码，摘自 application.cc
void Application::Run() {
    while (true) {
        EventBits_t bits = xEventGroupWaitBits(
            event_group_,
            MAIN_EVENT_SCHEDULE | MAIN_EVENT_NETWORK_CONNECTED |
            MAIN_EVENT_WAKE_WORD_DETECTED | MAIN_EVENT_TOGGLE_CHAT | ...
        );

        if (bits & MAIN_EVENT_SCHEDULE)      HandleSchedule();       // 执行 Schedule() 排队的回调
        if (bits & MAIN_EVENT_NETWORK_CONNECTED) HandleNetworkConnected();
        if (bits & MAIN_EVENT_WAKE_WORD_DETECTED) HandleWakeWord();
        if (bits & MAIN_EVENT_TOGGLE_CHAT)   HandleToggleChat();
        // ...
    }
}
```

### Schedule 机制

跨任务操作主任务上的东西（比如 LVGL 显示、UI 操作）是危险的。所以任何其他任务想碰 UI，都调用 `Application::Schedule([](...){ ... })` 把 lambda 排队，主任务会在下次循环时执行它。MCP 工具回调里也用了这个机制。

## DeviceState 状态机

设备有一个显式的状态机：

```
kDeviceStateStarting → kDeviceStateWifiConfiguring → kDeviceStateIdle
                                                    ↓
                                            kDeviceStateConnecting
                                                    ↓
                                             kDeviceStateListening
                                                    ↓
                                            kDeviceStateSpeaking → kDeviceStateIdle
                                                    ↑
                                             kDeviceStateConnecting
```

每次状态切换时触发 `OnStateChanged(old, new)`，那里会处理表情变化、音效、音频通道的开关。

## 线程/任务模型

ESP32-S3 是双核（Core 0 + Core 1），固件把任务分配到不同核上并行跑：

| 任务 | 核 | 优先级 | 职责 |
|------|----|--------|------|
| 主任务 (main) | 0 | 默认 | 事件循环、UI 操作、MCP 回调 |
| robot_task | 0 或 1 | 高 | 机器人运动控制循环（步态、平衡） |
| motor_rx_task | 1 | 高 | 舵机串口读取 + IMU 读取 |
| AudioService 内部任务 | 不定 | 中高 | I2S 音频采集、Opus 编码 |
| WiFi 任务 | 系统 | 系统 | WiFi 连接管理 |
| OTA 任务 | 系统 | 中 | 版本检查、固件下载 |

**注意到什么了？** MCP 工具最终是被主任务执行的（通过 `app.Schedule` 排队），这意味着工具回调里可以安全地操作 LVGL 显示、播放音效、改设备状态——不会跟主循环打架。

## Board 抽象层设计

```
Board (基类, boards/common/board.h)
├── WifiBoard (boards/common/wifi_board.h)
│   ├── PuppyBoard    (boards/puppy/puppy_board.cc)
│   ├── HoverBoard    (boards/hover/hover_board.cc)
│   ├── ArmBoard      (boards/arm/arm_board.cc)
│   └── TarsBoard     (boards/tars/tars_board.cc)
```

每个 Board 子类要做的事：
1. **构造函数里**初始化 SPI/I2C/UART/GPIO 等硬件
2. **实现 `InitializeTools()`**：注册自己形态的 MCP 工具
3. **实现 `OnStartup()`、`OnWifiConfigStart()` 等钩子**：让框架在合适时机调用
4. **暴露硬件接口**：`GetAudioCodec()`、`GetDisplay()`、`GetCamera()` 等返回对应驱动实例

框架代码（Application、McpServer、AudioService）全部只依赖 Board 基类的虚函数，完全不知道底下是 Dog 还是 Hover。
